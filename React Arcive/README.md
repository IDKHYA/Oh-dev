# React Archive 모바일 확장 및 구조 개선 최최종 계획서

## 1. 문서 목적

이 문서는 현재 존재하는 `React Archive` 시스템을 기준으로

1. 지금 구조를 정확히 이해하고
2. 현재 코드의 문제점을 정리하고
3. 휴대폰에서도 사용할 수 있는 형태로 확장하며
4. 장기적으로도 무너지지 않는 방향으로 구조를 개선하기 위한
   최종 개발 계획을 정의하기 위해 작성되었습니다.

이 문서는 단순히 “무엇을 만들까” 수준의 문서가 아닙니다.
이미 존재하는 코드를 역으로 분석한 뒤, **현재 구조의 한계와 실제 개선 방향을 합쳐서 하나의 실행 가능한 계획**으로 재정리한 문서입니다.

---

## 2. 프로젝트를 한 문장으로 정의하면

이 프로젝트는 **React 코드를 저장하고 분류하고 다시 실행해볼 수 있는 개인용 아카이브 시스템**입니다.

조금 더 정확히 말하면,
생성형 AI나 직접 작성한 React 코드를 하나의 결과물 단위로 저장해두고,
제목과 개요를 붙여 관리하고,
웹에서 다시 열어 즉시 실행해보는 **개인용 React 콘텐츠 보관 및 실행 도구**입니다.

즉 이 시스템의 본질은 일반적인 코드 저장소가 아니라
**“React 결과물 아카이브 + 뷰어 + 간단 편집기”**입니다.

---

## 3. 현재 시스템의 상태 요약

현재 시스템은 Next.js 기반으로 만들어져 있으며, 데이터베이스 없이 **파일시스템 기반 저장 구조**를 사용하고 있습니다.

구조를 요약하면 다음과 같습니다.

* 웹 화면에서 제목, 개요, 코드 입력
* 서버가 이를 `react_contents` 폴더 아래에 저장
* 각 콘텐츠는 `metadata.json`과 `content.jsx` 파일로 구성
* 저장된 콘텐츠는 다시 목록에서 불러와 실행 가능
* 폴더 단위 분류 가능
* 실행 화면에서 코드 보기와 일부 수정 가능

즉 현재 버전은 이미 작동하는 프로토타입입니다.
다만 구조적으로는 **개인 PC에서만 돌아가는 파일 기반 실험형 도구**에 가깝고,
모바일 사용성과 장기 유지보수를 고려한 설계는 아직 부족합니다.

## 4. 현재 시스템의 실제 정체

이 계획을 제대로 이해하려면, 현재 시스템이 무엇인지부터 정확히 잡아야 합니다.

이 시스템은 다음 중 어디에 가까운가를 보면 됩니다.

* 정식 배포용 서비스
* 일반적인 CMS
* 클라우드형 코드 저장소
* 개인용 생산성 툴
* AI 생성 결과물 보관함

정답은 마지막 두 가지입니다.

현재 시스템은 **개인용 생산성 툴**이며 동시에 **AI가 생성한 React 결과물을 보관하고 다시 실행해보는 아카이브 시스템**입니다.

이 정의가 중요한 이유는 앞으로의 기술 선택이 여기에 따라 달라지기 때문입니다.
지금 당장 멀티유저 SaaS처럼 설계할 필요는 없고,
반대로 지금 구조를 계속 파일 기반으로 끌고 가도 모바일과 확장성 측면에서 금방 한계가 옵니다.

즉 현재 프로젝트의 가장 올바른 방향은

**“혼자 쓰는 도구답게 단순하게 유지하되, 구조는 앞으로 커질 수 있게 정리하는 것”**

입니다.

## 5. 현재 코드에서 확인된 핵심 문제

이번 계획은 단순히 기능 추가가 아니라 **기존 코드의 구조적 문제를 바로잡는 작업**도 함께 포함합니다.
지금 이 부분을 제대로 정리하지 않으면, 모바일 확장만 붙여도 오히려 시스템이 더 불안정해집니다.

### 5-1. 저장 방식이 파일시스템에 강하게 묶여 있습니다

현재는 모든 콘텐츠가 폴더와 파일 형태로 저장됩니다.
이 방식은 초기 구현이 쉽고 눈에 보이는 장점이 있지만, 휴대폰이나 외부 접속까지 고려하면 구조가 빠르게 불안정해집니다.

문제는 다음과 같습니다.

* 경로가 곧 데이터 구조가 됨
* 폴더명과 저장 위치가 강하게 결합됨
* 이동, 이름변경, 조회가 모두 파일 경로에 의존함
* 데이터 정렬, 검색, 필터링, 최근순 조회가 비효율적임

즉 지금 구조는 “보관은 되지만 서비스형 사용에는 약한 구조”입니다.

---

### 5-2. 수정 로직의 계약이 깨져 있습니다

현재 폴더 상세 화면에서는 콘텐츠 제목과 개요를 수정하려고 할 때, 코드까지 함께 업데이트한다고 가정하는 흐름이 들어 있습니다.
그런데 목록 조회 API는 실제 코드 내용을 내려주지 않습니다.

결과적으로 화면에서 수정 요청을 보낼 때 `code`가 없는 상태가 생기고,
서버 쪽에서는 코드가 있다고 가정하고 처리하려 하므로 수정 실패 가능성이 생깁니다.

이건 단순 버그가 아니라 **API 역할 설계가 섞여 있는 문제**입니다.

즉 지금은

* 메타데이터 수정
* 코드 수정
* 폴더 이동

이 3가지가 한 API 안에 뒤엉켜 있습니다.

---

### 5-3. 폴더명이 곧 식별자라서 URL 안정성이 약합니다

현재는 폴더명이 URL과 파일 경로와 UI 표시값을 동시에 담당합니다.
이 구조에서는 한글, 특수문자, `#`, 공백, 퍼센트 인코딩 문제가 바로 드러납니다.

실제로 이 프로젝트 안에도 폴더명이 깨져 보이는 사례가 확인됩니다.

즉 현재는

* 화면 표시용 이름
* URL 파라미터
* 저장 경로명

이 3개가 분리되어 있지 않습니다.

이 구조는 규모가 작을 때는 버티지만, 폰에서 접속하고 주소를 공유하고 터널 URL까지 얹는 순간 불안정성이 더 커집니다.

---

### 5-4. 대시보드가 비효율적으로 동작합니다

현재 대시보드는 전체 폴더를 먼저 가져온 뒤, 각 폴더를 다시 순회하면서 콘텐츠 목록을 하나씩 불러옵니다.
즉 폴더 수가 늘수록 요청 수도 함께 늘어나는 방식입니다.

현재는 데이터가 적어서 괜찮지만, 구조 자체는 좋지 않습니다.

휴대폰 환경에서는 특히 이런 방식이 더 체감됩니다.

* 네트워크 요청이 늘어남
* 목록 진입 속도가 불안정해짐
* 화면 로딩 체감이 나빠짐

---

### 5-5. 경로 검증이 없어 구조적으로 위험합니다

현재 파일 접근 함수들은 사용자 입력값을 경로에 그대로 붙이는 식으로 동작합니다.
개인용 도구에서는 크게 체감되지 않을 수 있지만, 구조적으로는 좋지 않습니다.

즉 지금은 보안 사고를 걱정하는 단계보다
**애초에 설계가 경로 안전성을 충분히 고려하지 않았다**는 점이 더 중요합니다.

이 문제는 DB 전환 과정에서 자연스럽게 정리하는 것이 가장 좋습니다.

---

### 5-6. 실행 구조가 개인용 도구 수준에 머물러 있습니다

현재 저장된 React 코드는 브라우저에서 그대로 실행됩니다.
이 방식은 개인이 직접 만든 코드만 다룰 때는 충분히 실용적입니다.
하지만 외부 공유나 멀티유저 구조로 넘어가면 보안과 격리 문제가 생길 수 있습니다.

다만 이 문제는 지금 당장 “전체 구조를 갈아엎어야 한다”는 뜻은 아닙니다.
현재 단계에서는 **개인용 사용을 전제로 유지하되, 장기적으로는 실행 격리 구조를 고려해야 한다** 정도로 정의하면 됩니다.

---

### 5-7. 현재 패키징 상태는 재현성이 낮습니다

압축본 기준으로 보면 `.next`와 `node_modules`가 함께 들어 있고, 플랫폼 종속성이 섞여 있습니다.
즉 지금 상태는 “깔끔한 배포용 저장소”가 아니라 “작업하던 개발 환경의 복사본”에 가깝습니다.

이건 실사용에서 가장 먼저 터지는 문제는 아니지만, 앞으로 시스템을 안정적으로 유지하려면 반드시 정리해야 하는 지점입니다.

## 6. 이 프로젝트가 앞으로 가야 할 방향

이제 방향을 분명히 정리하겠습니다.

이 프로젝트의 목표는 **앱을 새로 만드는 것**이 아닙니다.
또한 **백엔드를 거창하게 분리하는 것 자체**도 목표가 아닙니다.

진짜 목표는 다음입니다.

### 핵심 목표

* 지금의 React Archive를 유지한다
* 저장 구조를 더 안정적으로 바꾼다
* 휴대폰에서도 접속 가능하게 만든다
* 바깥에서도 사용할 수 있게 네트워크를 연다
* 지금은 혼자 쓰되 나중에 확장 가능성은 남겨둔다

즉 이 계획은 **기존 시스템을 버리는 계획이 아니라, 프로토타입을 실사용 가능한 개인용 시스템으로 끌어올리는 계획**입니다.

## 7. 최종 구조 결정

여기서 가장 중요한 결정을 명확히 남기겠습니다.

### 최종 기술 방향

* Kotlin 앱: **지금 단계에서는 도입하지 않음**

이게 이번 프로젝트의 최종 방향입니다.

## 8. 왜 Spring Boot가 아니라 Next.js 유지인가

이 결정은 아주 중요합니다.

처음 보기엔
“모바일도 쓸 거고 DB도 붙일 거면 백엔드를 Spring Boot로 따로 만드는 게 더 정석 아닌가”
라는 생각이 들 수 있습니다.

하지만 지금 프로젝트에서는 그게 최적이 아닙니다.

이유는 다음과 같습니다.

### 첫째

이미 Next.js 기반 화면과 흐름이 완성되어 있습니다.
지금 필요한 것은 “백엔드 분리”보다 “현재 구조를 안정화하고 모바일에서도 쓸 수 있게 하는 것”입니다.

### 둘째

사용자는 현재 1명입니다.
멀티유저 인증 시스템도 없고, 외부 서비스 배포도 당장 목표가 아닙니다.
이 상황에서 백엔드를 따로 나누면 얻는 이점보다 관리 복잡도가 더 커집니다.

### 셋째

지금은 개발 속도가 중요합니다.
Spring Boot를 도입하면 다음이 한 번에 늘어납니다.

* 별도 서버 프로젝트 관리
* CORS 처리
* API 명세 중복 관리
* DTO 계층 설계
* 프론트와 백엔드 동시 배포
* 로컬 실행 환경 이원화

지금은 이 비용을 낼 시점이 아닙니다.

### 결론

현재는 **Next.js 안에서 API와 화면을 함께 유지하면서 DB로만 전환하는 방식**이 가장 합리적입니다.

Spring Boot는 나중에 정말 필요해질 때 분리해도 늦지 않습니다.

---

## 9. 왜 Kotlin 앱이 아니라 모바일 웹인가

이 부분도 분명히 하겠습니다.

지금 목표는 **핸드폰에서 내 시스템을 쓸 수 있게 하는 것**입니다.
이 목표만 놓고 보면 Kotlin 앱은 필수가 아닙니다.

오히려 지금은 모바일 웹이 더 적합합니다.

### 이유

* 기존 UI를 재사용할 수 있음
* 별도 앱 개발이 필요 없음
* 브라우저로 바로 접속 가능
* 업데이트 즉시 반영 가능
* 터널 주소만 있으면 어디서든 접속 가능

즉 지금은 앱보다 **반응형 웹 + 모바일 브라우저 접근**이 정답입니다.

나중에 아래 조건이 생기면 Kotlin 앱을 검토하면 됩니다.

* 플레이스토어 배포가 필요할 때
* 네이티브 앱 UX가 꼭 필요할 때
* 푸시 알림, 오프라인 저장, 백그라운드 처리 등 앱 기능이 중요해질 때

현재는 그 단계가 아닙니다.

## 10. 왜 DB가 필요한가

이 계획의 핵심 전환점은 파일시스템에서 DB로 넘어가는 것입니다.

이유는 명확합니다.

현재 파일 저장 방식은

* 구현은 쉽지만
* 조회와 수정이 비효율적이고
* 경로 중심 구조라 확장성이 떨어집니다.

반면 DB로 전환하면 다음이 좋아집니다.

* 목록 조회가 빨라짐
* 최근 콘텐츠 정렬이 쉬워짐
* 제목, 개요, 수정일 관리가 쉬워짐
* 모바일에서도 일관된 데이터 접근 가능
* API 설계가 단순해짐
* 나중에 검색, 태그, 사용자 확장이 쉬워짐

즉 DB 전환은 단순 저장소 변경이 아니라,
**이 프로젝트를 “파일 묶음”에서 “관리 가능한 데이터 시스템”으로 바꾸는 작업**입니다.

## 11. 데이터 구조의 최종 정의

현재 목적에 가장 적합한 저장 단위는 `content`입니다.
지금은 사용자 구분이 없으므로 콘텐츠 자체를 기준으로 깔끔하게 설계합니다.

### content의 기본 구조

* `id`
* `title`
* `summary`
* `code`
* `folder_name`
* `created_at`
* `updated_at`

이 구조로 시작하는 것이 가장 적절합니다.

여기서 중요한 판단은 **파일경로를 핵심 필드에서 제외한다**는 점입니다.

현재는 파일 기반 구조였기 때문에 “파일경로도 저장해야 하나”라는 생각이 자연스럽지만,
DB 구조에서는 파일경로가 중심이 되면 안 됩니다.

이제 저장의 기준은 파일이 아니라 **레코드**입니다.

즉 앞으로 이 시스템의 정체는

* 파일을 찾는 시스템이 아니라
* 콘텐츠를 찾는 시스템

이 되어야 합니다.

---

## 12. 폴더 개념은 어떻게 가져갈 것인가

현재 폴더는 실제 디렉터리이자 표시 이름이자 URL 일부입니다.
이 구조는 앞으로 분리해야 합니다.

이번 계획에서 폴더는 **논리적 분류 단위**로만 사용합니다.

즉 지금 단계에서는 `folder_name` 정도로 단순하게 두되,
내부 구조는 나중에 다음처럼 확장 가능하게 생각합니다.

* 표시용 폴더명
* 내부 폴더 ID
* 정렬 순서
* 생성일

하지만 이번 단계에서는 너무 무겁게 가지 않고
**“폴더는 콘텐츠 분류용 필드”**로 두는 것이 맞습니다.

즉 지금은 폴더를 먼저 완벽한 도메인으로 만들기보다,
콘텐츠 중심 설계를 우선합니다.

## 13. 네트워크 구조의 최종 정의

이번 프로젝트에서 네트워크는 이렇게 정의합니다.

### 최종 네트워크 구조

* 집이나 작업용 PC가 서버 역할을 한다
* Next.js 앱이 PC에서 실행된다
* SQLite는 PC 내부에서 같이 동작한다
* Cloudflare Named Tunnel이 이 로컬 서버를 외부에 연결한다
* 휴대폰은 브라우저로 해당 주소에 접속한다

즉 휴대폰이 DB에 직접 붙는 구조가 아닙니다.
휴대폰은 오직 웹 서버만 봅니다.

이게 중요합니다.

따라서 네트워크를 위해 필요한 것은

* 네트워크형 DB 서버 구축이 아니라
* **웹 앱을 외부에서 열 수 있게 만드는 연결 계층**

입니다.

그 역할을 이번에는 Cloudflare Named Tunnel이 맡습니다.

## 14. 모바일에서 실제로 어떻게 쓰게 되는가

최종 사용 시나리오는 아주 단순해야 합니다.

사용자는 휴대폰에서 다음처럼 씁니다.

1. 브라우저를 연다
2. 고정된 터널 주소로 접속한다
3. 목록을 본다
4. 콘텐츠를 연다
5. 제목과 개요를 수정한다
6. 필요하면 코드를 본다
7. 실행 결과를 확인한다

즉 폰에서는 별도 앱 설치보다 **접속성과 즉시성**이 더 중요합니다.

이 문서의 전체 방향도 여기에 맞춰져 있습니다.

## 19. 단계별 전체 추진 전략

이번 프로젝트는 한 번에 크게 만드는 방식보다, **기존 시스템을 유지하면서 단계적으로 안정화하는 방식**이 맞습니다.

### 1단계: 구조 안정화

가장 먼저 해야 할 것은 기존 코드를 모바일로 옮기는 것이 아니라,
**현재 구조의 불안정한 부분을 정리하는 것**입니다.

이 단계의 핵심은 다음입니다.

* 저장 구조를 파일 기준에서 데이터 기준으로 전환할 준비
* API 책임 정리
* 폴더명과 URL 문제 완화
* 수정 로직 오류 가능성 제거

즉 지금은 “예쁘게 만드는 단계”가 아니라 “망가지지 않게 만드는 단계”입니다.

---

### 2단계: DB 전환

그다음 핵심 전환은 DB 도입입니다.

이 단계가 끝나면 시스템의 중심이 더 이상 `react_contents` 폴더가 아니라 DB가 됩니다.

이 변화가 중요한 이유는 다음과 같습니다.

* 조회 방식이 단순해짐
* 수정과 이동 개념이 정리됨
* 최근순 정렬이 쉬워짐
* 모바일 환경에서도 일관성 있는 응답 가능
* 이후 검색이나 태그 같은 기능 확장이 쉬워짐

이번 프로젝트에서 가장 본질적인 전환은 이 단계입니다.

---

### 3단계: 모바일 실사용화

DB 전환만 끝나면 폰에서 쓸 수 있는 것은 아닙니다.
실제로는 UI를 모바일 기준으로 다시 다듬어야 합니다.

이 단계에서 중요한 것은 다음입니다.

* 목록 화면 가독성
* 상세 화면 스크롤 구조
* 코드 보기와 실행 보기 전환
* 손가락으로 누르기 쉬운 버튼 크기
* 불필요한 복잡도 제거

즉 모바일 지원은 단순히 “화면이 줄어든다”가 아니라
**사용 흐름을 다시 설계하는 일**입니다.

---

### 4단계: 외부 접속 연결

그 다음 단계가 Cloudflare Named Tunnel입니다.

이 단계가 완료되면 사용자는 같은 와이파이 안이 아니어도,
휴대폰에서 자신의 시스템에 접속할 수 있습니다.

즉 이 단계는 모바일 지원을 “실내 테스트 수준”에서
“실제 개인용 운영 수준”으로 끌어올리는 단계입니다.

---

### 5단계: 운영 정리

마지막으로는 기술 구현보다 운영 관점 정리가 필요합니다.

예를 들면 다음 같은 부분입니다.

* 서버는 어떻게 켜는가
* 터널은 어떻게 같이 띄우는가
* DB는 어떻게 백업하는가
* PC가 꺼져 있으면 어떻게 되는가
* 폰에서는 주로 무엇까지 하는가

이 단계까지 정리되어야 비로소 “만들었다”가 아니라 “실제로 쓴다”가 됩니다.

## 24. 최종 결론

이 프로젝트의 최종 방향은 다음과 같이 정리됩니다.

현재 React Archive는 이미 의미 있는 프로토타입입니다.
하지만 지금 상태는 파일 기반 저장 구조와 혼합된 API 책임, URL 안정성 문제, 모바일 사용성 부족 때문에 실사용 단계로 올라가기엔 한계가 있습니다.

따라서 이번 계획의 핵심은 다음입니다.

* 기존 Next.js 구조는 유지한다
* 파일 기반 저장은 DB 중심으로 바꾼다
* 구조적으로 깨질 수 있는 부분을 먼저 바로잡는다
* 모바일 반응형으로 실제 사용 가능하게 만든다
* Cloudflare Named Tunnel로 외부 접속 가능하게 만든다
* 지금은 1인 사용에 집중한다
* Spring Boot와 Kotlin은 이후 필요 시점까지 보류한다

즉 이 프로젝트의 최최종 방향은

**“기존 React Archive를 버리지 않고, DB 기반으로 안정화한 뒤, 모바일 브라우저와 터널을 통해 언제 어디서든 접근 가능한 개인용 React 아카이브 시스템으로 발전시키는 것”**

입니다.
